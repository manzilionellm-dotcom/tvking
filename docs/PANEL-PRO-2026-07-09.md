## 1. Ce qui a été construit

### A. Séparation activation ↔ sources (demande n°1)

- **`/activate`** ne gère plus QUE l'abonnement (licence). Le bloc « trio de
  sources » a été retiré ; après une activation réussie, un bouton envoie sur
  la page Sources avec la MAC pré-remplie.
- **`/sources` (nouvelle page « Sources M3U / Xtream »)** :
  - inventaire automatique de ce que la MAC a déjà (sources panel + playlists
    ajoutées par le client, badgées) ;
  - édition / remplacement de 1 à 3 sources, champ EPG ;
  - **⚡ Test en direct** avant de pousser : `POST /api/v1/source-check`
    interroge le vrai serveur (Xtream `player_api.php` : statut, échéance,
    connexions max/actives ; M3U : lecture des premiers 256 Ko, `#EXTM3U`,
    nombre de chaînes détectées, latence). *N'importe quel M3U, vérifié en ~2 s.*
  - poussée + confirmation de livraison instantanée (révision de synchro).

### B. Livraison instantanée (demande n°2)

Mécanisme **rev/poll** de bout en bout :

1. Le Worker tient une **révision de synchro par MAC** (table `device_sync`,
   ligne `*` = révision globale). Chaque action panel la bumpe : activation,
   renouvellement, source poussée/retirée, gel/ban/dégel, suppression,
   transfert, membre famille retiré, self-service client, grant-trial-all,
   accès app, publication produit.
2. **`GET /api/sync/:mac`** (public, ultra-léger, rate-limité) renvoie
   `{ rev, access, next }`.
3. **L'app poll toutes les ~20 s** (`lib/features/playlists/data/remote_sync_poller.dart`,
   branché dans les 4 mains : mobile, TV, Windows, Tizen). Révision changée →
   re-synchro IMMÉDIATE des sources **et du statut d'abonnement**.
   - Avant : sources ≤ 5 min, statut ≤ 6 h (TV). Maintenant : **≤ 20 s**.
   - Repli automatique sur l'ancien cycle 5 min si le Worker déployé
     n'expose pas encore `/api/sync` (aucune rupture pendant la transition).
   - Le délai `next` est piloté côté serveur : on peut ralentir tout le parc
     sans mise à jour d'app.

### D. Sécurité (demande n°4)

- **Révocation de session** : un JWT est refusé si le compte a été
  désactivé/suspendu ou si le mot de passe a changé après l'émission du jeton
  (colonne `password_changed_at`, cache 60 s par isolate, fail-open si la
  migration n'est pas passée). Un jeton volé meurt au changement de mot de passe.
- Le login par **clé maître** (`ADMIN_SECRET`) révoque aussi les anciens jetons.
- **Audit des connexions** : `auth.login` / `auth.login_failed` (IP + UA).
- Mot de passe revendeur : minimum 8 caractères aussi côté reset admin ;
  **plus aucun hash de mot de passe dans l'audit log** (fuite corrigée).
- **Clés API** stockées hachées (jamais relisibles), scopes en liste blanche,
  rate-limit dédié anti-brute-force.
- **Webhooks** : HTTPS obligatoire, signature HMAC, timeout 5 s, best-effort
  (ne bloquent jamais l'action métier).
- **Panel (Cloudflare Pages)** : `public/_headers` — CSP stricte (aucune
  ressource tierce), `X-Frame-Options: DENY`, HSTS, nosniff, Referrer-Policy,
  Permissions-Policy. L'`@import` Google Fonts (déjà non fonctionnel) retiré.
- Smoke tests sécurité étendus : **11/11** (fail-open sans D1 des nouveaux
  endpoints, MAC invalide → 400, clé API inconnue → refusée).
- Correctif visuel de fond : les couleurs `success`/`warn` utilisées par les
  badges n'existaient pas dans la palette Tailwind (badges invisibles) —
  ajoutées.

## 2. Déploiement

1. **Worker** : `cd cloudflare && npx wrangler deploy` (aucune migration
   manuelle : toutes les nouvelles tables se créent d'elles-mêmes au premier
   usage — `device_sync`, `products`, `api_keys`, `webhooks`, colonnes
   `password_changed_at`).
2. **Panel** : build Cloudflare Pages habituel (`npm run build` dans
   `admin-panel/`) — `_headers` part automatiquement avec `dist/`.
3. **Apps** : rebuild CI habituel (mobile + TV). Les anciennes apps restent
   100 % fonctionnelles (elles ignorent `/api/sync` et gardent leurs cycles).
