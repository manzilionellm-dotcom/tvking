## 3. Résultat de revue du formulaire original

- M3U reste le choix par défaut ; Xtream requiert serveur HTTP(S), identifiant et password, validés avant l'envoi.
- Ajouter conserve toutes les sources du panel, leur ordre, label, EPG, credentials et état enabled:false ; les sources origin:self ne sont pas renvoyées et restent conservées par le Worker.
- Même identité Xtream serveur+identifiant : mise à jour des accès au même emplacement ; quatrième source distincte du panel : refus avant PUT. Remplacer : nouvelle source seule et conservation des sources self côté serveur.
- La MAC virtuelle exacte est normalisée sans rapprochement avec un code voisin. Les GET tardifs d'un ancien appareil sont ignorés ; la MAC est désactivée pendant un envoi. L'aperçu affiche uniquement l'appareil correspondant au code saisi.
- L'écran Listes appelle les routes sources et ordres, jamais activation. Les tests locaux vérifient les licences inchangées.

Ces propriétés sont établies pour les scénarios testés. Le code ne justifiait pas une garantie générale de conservation entre plusieurs opérateurs : le défaut ci-dessous était encore présent.

## 4. Défauts reproductibles corrigés dans la proposition isolée

### A. Perte d'une liste entre deux onglets — priorité élevée

Reproduction sur la fonction planAddSource de production, Worker.fetch et SQLite : deux onglets lisent [A éteinte, self], le premier ajoute M3U B, le second ajoute Xtream C depuis son ancienne lecture. Les deux PUT répondent 200 ; B disparaît. Autre MAC et licences restent inchangées. Ce défaut est antérieur à #104.

Correction : GET renvoie sources et rev dans une seule instruction SQL. Le formulaire transmet expected_rev avec PUT/DELETE. La condition est vérifiée dans le lot transactionnel, y compris après suppression/recréation ou lorsqu'une source arrive entre lecture et écriture. Snapshot périmé : 409 sources_conflict, sans nouvelle source/révision/ordre/licence. L'écran relit l'état, garde la saisie et laisse l'opérateur réessayer après inspection ; aucun rejeu automatique d'un remplacement destructeur.

La précondition reste optionnelle pour conserver le contrat des anciens clients. **Les autres écrans ou clients qui omettent expected_rev restent exposés aux remplacements concurrents.** Il faut le nouveau Worker et le formulaire corrigé pour bénéficier de la protection ; installer le seul formulaire contre un ancien Worker ne l'établit pas.

### B. Accusé d'une mauvaise révision — priorité élevée

Reproduction sur le Worker et SQLite : créer ordre1/révision1 puis ordre2/révision2 ; accuser ordre1 avec config_rev=2. Avant correction, ordre1 devient APPLIED et révision2 ACKNOWLEDGED malgré l'absence d'ACK de son propre ordre. Ce défaut est antérieur à #104.

Correction : si config_rev est fourni et diffère de celui de l'ordre, RECEIVED/APPLIED/FAILED sont refusés avant toute écriture : résultat individuel 409 config_revision_mismatch. Ordre, révisions et licences restent identiques. Bonne révision et doublons valides restent acceptés.

Le POST batch peut répondre HTTP 200 avec un résultat individuel refusé ; vérifier results[i].status. Les anciens ACK sans config_rev restent compatibles et ne confirment aucune révision. Ils peuvent néanmoins terminer un ordre : l'étiquette APPLIED seule n'établit donc pas une preuve complète de révision ni de lecture vidéo.

## 7. Recette physique et décision suivante

Protocole détaillé : [validation-tv-pr104-20261009.md](validation-tv-pr104-20261009.md).

Avant tout essai réel, relever le SHA panel, SHA Worker, SHA/digest/versionCode/package/signature APK, backend effectivement utilisé et flags compilés. Employer deux appareils et des sources maîtrisées dans un environnement isolé. Le domaine API codé dans un APK peut viser la production même si le panel est local : vérifier la destination réelle avant d'envoyer une mutation.

Priorités :

1. Activation et ajout M3U/Xtream réellement visibles et lisibles sur A, B inchangée ; licenses/ledger invariants pour les opérations de listes.
2. Rotation du password du même Xtream, ancien accès invalidé : nouvelle clé réellement utilisée sans doublon ni perte d'ID/favoris/sélection.
3. RECEIVED puis APPLIED/FAILED émis par la TV, même MAC/order_id/config_rev ; refus mauvaise révision et inspection des résultats batch. Aucun ACK fabriqué par le testeur.
4. Sources éteintes/self/locales, remplacement explicite, retrait, reboot et reconnexion, fournisseur invalide et échec partiel ; état local durable vérifié.
5. 30 répétitions par opération/transport pour n, échecs, p50/p95/min/max ; séparer réception, import, affichage et première lecture, sans soustraire des horloges non synchronisées. Aucun seuil ou résultat instantané n'est inventé.
6. Régression D-pad, Direct/Cinéma, EPG, profils/favoris, replay, enregistrement et cast sur l'APK candidat.

**Décision : conserver #104 et les corrections d'audit en revue. Ne pas fusionner ni déployer tant que le binaire TV et la recette physique ne sont pas établis, puis obtenir la validation explicite du propriétaire.**
